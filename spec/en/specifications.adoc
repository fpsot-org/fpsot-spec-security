= Flaws in specifications
include::_fpsot-terms.adoc[]

A {term-vulnerability} can sit in code, but also in one of the specifications of the {abbr-fpsot-first}.
These rules set how a person reports such a flaw, and how the security team fixes and releases it.

A security flaw in a specification is one of these:

* a rule whose correct implementation creates a {term-vulnerability};
* a missing rule, whose absence leaves every conforming implementation exposed;
* an example or a template that is unsafe to copy.

[[SEC-070]]
*SEC-070.* A person MUST report a security flaw in a specification through the private channels of SEC-040.
The specification's Working Group MUST NOT receive or discuss the flaw before its public release.
Its issues, pull requests, meetings and mailing lists are Working Group activity.
Section 5 of the link:https://github.com/CommunitySpecification/Community_Specification/blob/8a05e46d768ac0525af882b619c42f3380a9e869/05-governance.md[governance file of the Community Specification 1.0] says that all of it is not confidential.

[[SEC-071]]
*SEC-071.* The security team MUST prepare the fix outside the Working Group repositories, such as in a private fork.
It MAY ask a maintainer of the specification to help, under these conditions:

* the maintainer signs the pledge of SEC-042, and the record of SEC-048 names them;
* the maintainer acts as an individual, not for the Working Group or for an employer;
* the maintainer does not count toward the three members of SEC-042;
* the maintainer does not use the information for an employer before the pre-notice.

The fix then reaches the Working Group as a contribution at its public release.
A fix drafted in the open would show the flaw before implementers can act.

[[SEC-072]]
*SEC-072.* The fix MUST ship as a patch release of each supported version, even when it changes a rule.
The changelog MUST list it under a `Security` heading, and MUST state each rule that changed.
A patch release reaches implementers quickly, and the changelog shows them what to change in their code.

[[SEC-073]]
*SEC-073.* A security flaw in a specification MUST follow the pre-notice and the dates of SEC-050 to SEC-059.
The security advisory MUST name the specification, its affected versions and the rules at fault.
The team MAY rate its severity as low, medium, high or critical, or score a conforming implementation under SEC-044.
The security team SHOULD request a {abbr-cve-first} identifier when a conforming implementation is vulnerable.
Implementers then get the same head start and the same public notice as users of the code.
