= FPSOT security specification
include::_fpsot-terms.adoc[]

This specification sets how the projects of the {abbr-fpsot-first} build, release and maintain their software and their specifications securely.
It also sets how a person reports a {term-vulnerability}, and how {abbr-fpsot} fixes and discloses it.

The rules name capabilities, not products.
They require no vendor tool and no paid service.
Tools appear only as examples.

The rules come in nine parts, and one informative page follows them.

* xref:development.adoc[Secure development] profiles a framework of the {abbr-nist-first}.
It also sets the threat model and the security requirements of each product.
* xref:code-review.adoc[Code, review and analysis] sets the second review of security-relevant changes, and the analysis that runs on each pull request.
* xref:secrets.adoc[Secrets] keeps secrets out of repositories and images, and sets their rotation.
* xref:supply-chain.adoc[Supply chain] pins dependencies and actions, and sets the bill of materials, the provenance and the signature of each release.
* xref:reporting.adoc[Reporting and handling vulnerabilities] sets the private channel, the times, the severity score, the identifiers and the advisories.
* xref:disclosure.adoc[Pre-notice and disclosure] sets the list of adopters that learn of a fix first.
It also sets the head start and the public release.
* xref:releases.adoc[Supported versions and security files] sets the supported versions, the end of support and the `SECURITY.md` file.
* xref:specifications.adoc[Flaws in specifications] sets how people report and fix a flaw in a specification.
* xref:security-tests.adoc[Security tests] ties the security tests to the testing specification.
* xref:legal-context.adoc[Laws and deadlines of recipients] is informative, and sums up the laws that touch on these rules.

== Related specifications

This specification builds on other {abbr-fpsot} specifications.
The version control specification sets the signed commits and tags and the protected branches.
The documentation specification sets the diagrams as code that a threat model uses.
The {abbr-api-first} design specification sets the security rules of each {abbr-api}, which the security tests check.
The testing specification sets the test levels and the required checks that run the security tests.

The future {abbr-fpsot} specifications on code and on capabilities will add the tools and settings of each language.

== Template

The file `examples/SECURITY.md` is a template that a repository copies.
It holds the policy in English and in French, and it meets SEC-063.

== Conformance

[quote, 'link:https://www.rfc-editor.org/info/rfc8174[RFC 8174]']
____
The key words "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL NOT", "SHOULD", "SHOULD NOT", "RECOMMENDED", "NOT RECOMMENDED", "MAY", and "OPTIONAL" in this document are to be interpreted as described in BCP 14 (link:https://www.rfc-editor.org/info/rfc2119[RFC 2119], link:https://www.rfc-editor.org/info/rfc8174[RFC 8174]) when, and only when, they appear in all capitals, as shown here.
____

The keywords follow requirement WRT-010 of the {abbr-fpsot} writing specification.
The French version uses the French keywords of WRT-011.

The rules address three parties.
A project conforms when its repositories, builds and releases meet every MUST rule that applies to them.
The {abbr-fpsot} security team conforms when it handles each report under SEC-040 to SEC-073.
A member of the pre-notice list accepts SEC-057 to SEC-059 as the terms of its membership.

== Which rules apply

Not every rule applies to every repository.
The table shows where each group of rules applies.
The repository of a software component holds code that {abbr-fpsot} releases as an artifact, such as an image.
A specification repository holds a specification, which {abbr-fpsot} releases as books in {abbr-html-first} and {abbr-pdf-first}.

[cols="2,2,2,1",options="header"]
|===
|Rules |Software component repository |Specification repository |Website
|SEC-001, SEC-002 |Yes |Yes |No
|SEC-003 to SEC-006 |Yes, for each product |No |No
|SEC-010 to SEC-017 |Yes |Yes, for the code and workflows it holds |No
|SEC-020 to SEC-024 |Yes |Yes |Yes
|SEC-030 to SEC-032 |Yes |Yes |Yes
|SEC-033, SEC-034 |Yes, for each artifact |No |No
|SEC-035, SEC-036 |Yes, for each artifact |SHOULD, for the books |No
|SEC-037 |SHOULD |SHOULD |No
|SEC-040 to SEC-059 |Yes |Yes, with SEC-070 to SEC-073 |Yes
|SEC-060 to SEC-064 |Yes |Yes |No
|SEC-065 |No |No |SHOULD
|SEC-070 to SEC-073 |No |Yes |No
|SEC-080 to SEC-084 |Yes |SEC-080 and SEC-084 only |No
|===

The {abbr-fpsot} organization itself meets SEC-050 to SEC-052, SEC-063 and SEC-064 only once its own `SECURITY.md` file exists.
The pages of the criteria and of the list of members must exist too.

== Legal status

The specification states the practice of {abbr-fpsot}, and it is not legal advice.
Points that need a lawyer sit in informative notes, never in a rule.

== Standards

The rules summarize outside standards in their own words and take no text from them.
They cite these versions:

* link:https://csrc.nist.gov/pubs/sp/800/218/final[NIST SP 800-218] version 1.1, since version 1.2 is still a draft;
* link:https://asvs.owasp.org/[OWASP ASVS 5.0.0];
* link:https://www.first.org/cvss/v4.0/specification-document[CVSS v4.0];
* link:https://slsa.dev/spec/v1.2/[SLSA v1.2];
* link:https://cyclonedx.org/specification/overview/[CycloneDX 1.7], with link:https://spdx.github.io/spdx-spec/v3.0.1/[SPDX 3.0.1] as an option.

This specification cites two standards on vulnerability disclosure by title only, because their text is not free to read.
They are link:https://www.iso.org/standard/72311.html[ISO/IEC 29147:2018, Vulnerability disclosure] and link:https://www.iso.org/standard/69725.html[ISO/IEC 30111:2019, Vulnerability handling processes].
